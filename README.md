# AI Business Workflow Automation System

> 基于开源工作流引擎 **[n8n](https://github.com/n8n-io/n8n)** + 大模型，把企业每天涌进来的**客户需求、表单、邮件、咨询**自动接住、听懂、分类、落库、通知到人。
> 不是 Demo，是一套把"人工分拣 → 手动录入 → 挨个喊人"这条老流程跑成**分钟级闭环**的企业级自动化系统。

---

## 一、企业痛点（改造前）

以一家 200 人 SaaS 公司"云启科技"为例，客户每天从 5 个入口进来：官网表单、邮件、企业微信、客服电话、小程序。原来的流程是这样运转的：

| 痛点 | 具体表现 | 业务代价 |
|---|---|---|
| **入口分散** | 客服早上要开 5 个后台挨个翻，漏看是常态 | 客户发了消息没人理，直接流失 |
| **靠人分类** | 凭经验分"售前/售后/技术/账单"，新员工常分错 | 客户被"踢皮球"，一个问题转 2-3 个人 |
| **手动录入** | 看完复制粘贴进 Excel，字段格式每人不一样 | 数据没法统计，周报靠人工拼 |
| **通知靠吼** | 微信上 @ 一下对应同事，人在开会就没了 | 紧急工单隔夜才被看到，投诉发酵 |
| **夜间真空** | 下班后、周末、节假日无人响应 | 客户在社交平台发负面评价 |
| **数据黑洞** | 工单散落在聊天记录里，事后复盘无据可查 | 产品不知道客户在抱怨什么 |

**核心矛盾**：每天上百条客户进线，但真正需要"人"去做的只有"专业处理客户问题"这一段；前面的搬运、读、分、录、通知，全是高成本低价值的人肉重复劳动。

## 二、自动化流程

```
客户在任何入口填写表单 / 发邮件 / 发消息
                ↓
   ① Webhook 统一接收（5 个入口打到一个地址）
                ↓
   ② LLM 需求分析：意图 / 情绪 / 紧急度
                ↓
   ③ AI 自动分类：售前/售后/技术/账单/合作/投诉/其他
                ↓
   ④ 自动生成 60 字摘要（负责人扫一眼就懂）
                ↓
   ⑤ 生成结构化工单（工单号 + 全字段）
                ↓
   ⑥ 同步飞书多维表格 / MySQL 业务库
                ↓
   ⑦ 按紧急度给负责人发飞书卡片（红=高危 / 橙=紧急 / 蓝=普通）
```

![工作流总览](assets/workflow-overview.png)

### 对应交付物

| 要求 | 交付物 |
|---|---|
| 1. 表单输入 | `form/index.html` —— 可直接打开的企业客服进线表单 |
| 2. AI 分析节点 | 工作流节点 ②：LLM 需求分析（意图/情绪/紧急度） |
| 3. 自动分类 | 工作流节点 ③：AI 智能分类（7 类，结构化输出强约束） |
| 4. 数据同步 | 工作流节点 ⑥：飞书多维表格 OpenAPI 写入（可扩展 MySQL） |
| 5. 消息通知 | 工作流节点 ⑦：飞书交互卡片，颜色随紧急度变化 |
| 模拟企业数据 | `simulation/sample-tickets.json` —— 25 条标注好的真实感工单 |

## 三、技术架构

![技术架构](docs/architecture.png)

五层结构 + 侧栏横切能力：

- **接入层**：官网表单、邮件、企微、客服电话、小程序 —— 全部以 Webhook 形式接入，不再逐个后台登录。
- **编排层（n8n）**：开源工作流引擎负责节点串联、条件路由、紧急度分支、错误重试、执行回执。**不写后端代码，业务流程可视化拖拽**。
- **AI 能力层**：接入 GPT-4o-mini（可替换任意 OpenAI 兼容接口），用结构化输出（Structured Output）强约束 LLM，不让它自由发挥。
- **数据层**：飞书多维表格作为业务人员可直接看的看板；MySQL 作为系统记录；审计日志独立留存。
- **触达层**：飞书卡片主通道，邮件/企微/短信作为升级通道，SLA 超时自动升级到主管。
- **横切能力**：凭据统一管理、执行日志全链路可追溯、失败重试、按角色权限、Token 成本监控。

### 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 工作流引擎 | n8n（自托管，AGPL） | 原生支持 AI 节点、飞书节点、Webhook |
| LLM | GPT-4o-mini（temperature 0.1） | 可替换为 DeepSeek / Qwen / 本地模型 |
| 数据存储 | 飞书多维表格 + MySQL | 业务人员看飞书，系统记录入 MySQL |
| 通知 | 飞书开放平台 IM 卡片 | 按紧急度换颜色，点击直达工单 |
| 前端表单 | 单文件 HTML | 无构建、无框架，直接部署 |

## 四、节省了哪些人工流程

| 原来靠人做的事 | 现在 | 每天节省 |
|---|---|---|
| 早上开 5 个后台翻未读消息 | Webhook 自动汇聚，0 等待 | 1~1.5 小时/人 |
| 读完留言判断归谁管 | LLM 自动分类 7 类 | 30~45 分钟/人 |
| 手动复制粘贴到 Excel | 结构化字段自动写入飞书表格 | 30 分钟/人 |
| 微信上 @ 同事派单 | 飞书卡片自动 @，按紧急度分级 | 15~30 分钟/人 |
| 高危投诉靠人盯 | critical 工单红色卡片秒级触达主管 | 加班/客诉成本大幅下降 |
| 每周手工拼客户报表 | 飞书表格即看板，可直接透视 | 每月 1 天人力 |

**合计**：一个 5 人客服团队，每天可释放约 **3~4 人时** 用于真正需要专业判断和客户沟通的工作，相当于**多出 0.5~0.7 个人力**，且 7×24 不打烊。

**量化对比（行业典型区间，上线后用真实数据校准）**：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 客户首次响应 | 数小时 ~ 1 个工作日 | 1 分钟内 |
| 工单错派率 | 15%~25% | < 5% |
| 高危工单隔夜未处理 | 每周 3~5 起 | ≈ 0 |
| 数据完整率 | 字段缺失、格式混乱 | 100% 结构化 |

## 六、怎么跑起来

1. **启动 n8n**：`docker run -it -p 5678:5678 n8nio/n8n`，浏览器打开 `http://localhost:5678`；
2. **导入工作流**：Workflows → Import from File → 选 `workflows/customer-inbox-ai-automation.json`；
3. **配凭据**：
   - OpenAI API Key；
   - 飞书自建应用，开通 `bitable:app` + `im:message` 权限；
4. **填环境变量**：`FEISHU_BITABLE_APP_TOKEN`、`FEISHU_BITABLE_TABLE_ID`、`FEISHU_OWNER_USER_ID`；
5. **打开表单**：双击 `form/index.html`，点"载入一条模拟客户"测试；
6. **看效果**：飞书多维表格多一行 + 负责人飞书弹出卡片。

批量验证 AI 分类准确率：把 `simulation/sample-tickets.json` 里的 25 条逐条 POST 到 Webhook，对比 AI 分类结果和文件里 `expected_category` 是否一致。

## 七、为什么这是"企业级"而不是玩具 Demo

- 入口统一，不是单点脚本；
- 用 **Structured Output** 强约束 LLM，不让它自由发挥；
- 关键写库 / 通知都有日志、可重试、可追溯；
- 紧急度路由：高危工单不会被淹没在普通咨询里；
- 节点职责单一：下个月加"合同类工单"、换模型、接企业微信，都只动一个节点；
- 业务人员自己能在飞书表格里看数据，**不依赖工程师**。
