# 节点说明

> 对应工作流文件：`workflows/customer-inbox-ai-automation.json`（主工作流，13 节点）+ `workflows/error-handler.json`（错误兜底，2 节点）
> 本文不只讲"这个节点怎么配"，更讲"这个节点替代了原来哪个人工动作、给业务带来什么改变"。

## 主工作流：节点清单（9 阶段 / 13 节点）

### ① 表单 / Webhook 接收（Webhook Trigger）

- **替代的人工动作**：客服每天早上去邮箱、企业微信后台、官网留言板挨个翻，把分散的咨询手动抄到一张 Excel 里。
- **现在做什么**：对外暴露一个统一入口 `POST /webhook/customer-inbox`。官网表单、企业微信机器人、邮件转发、第三方 SaaS 都打到同一个地址。
- **业务意义**：把"散落在 5 个地方的客户声音"收拢成一条流水线，不再漏看、不再重复登记。
- **关键配置**：`responseMode=responseNode`，处理完再回执，客户能立刻拿到受理编号。

### ② LLM 需求分析（Chain LLM · 模型温度 0.1）

- **替代的人工动作**：客服读完一大段客户留言，在脑子里判断"这是要退款？要退货？还是问发票？客户急不急？生气没生气？"
- **现在做什么**：把客户原话喂给大模型，强制输出结构化字段：
  - `intent`：一句话说清客户到底要什么
  - `sentiment`：情绪（positive / neutral / negative / angry）
  - `urgency`：紧急度（low / medium / high / critical）
  - `expectedAction`：希望企业下一步做什么
- **业务意义**：第一次让"客户的情绪和紧急度"变成可被系统处理的数据，而不是靠客服个人经验。
- **调优点**：本节点用 **temperature=0.1** 的专用模型节点（"OpenAI Chat Model（分析/分类）"），输出稳定、适合生产。

### ③ AI 智能分类（Chain LLM + Structured Output · 温度 0.1）

- **替代的人工动作**：前台/值班同事凭印象把工单分给销售、售后、技术、财务、商务——分错了客户就要被转两三次。
- **现在做什么**：LLM 从 7 个预置分类里选一个：
  `sales_inquiry`（售前咨询）/ `after_sales`（售后退换）/ `tech_support`（技术支持）/ `billing`（账单付款）/ `partnership`（商务合作）/ `complaint`（投诉）/ `other`（其他）。
- **业务意义**：
  - 新员工不用再背"什么单子该找谁"；
  - 错派率明显下降，客户少被"踢皮球"；
  - 每个分类的数据都能单独统计，管理者知道哪个部门工单最多。
- **为什么要单独一个节点而不是和②合并**：分析和分类是两件事——分析管"客户怎么了"，分类管"这事归谁管"。拆开后分类规则可以独立调整，不影响分析质量。

### ④ 知识库检索（RAG · HTTP Request）

- **替代的人工动作**：老员工凭记忆回答"这个政策是啥来着"，新员工问不到人就只能猜。
- **现在做什么**：把 ③ 得到的 `intent` 作为 query，调用知识库检索接口（`KB_SEARCH_URL`，可接 Qdrant / pgvector / 飞书知识库 / 任意搜索服务），取回 top-k 相关政策片段（`KB_TOP_K`）。仓库附带 `simulation/knowledge-base.md` 模拟知识库，可直接导入向量库测试。
- **业务意义**：
  - 摘要和后续回复**有依据、不编造**，回答口径与公司现行政策一致；
  - 知识沉淀从"人脑记忆"变成"可检索资产"，新人也能给出老员工水平的答案。
- **容错设计**：未配置 `KB_SEARCH_URL` 时节点自动跳过，摘要正常生成、不带知识库引用，不影响主流程。

### ⑤ 自动生成摘要（Chain LLM · 温度 0.4）

- **替代的人工动作**：负责人被 @ 之后还要自己点开原文、读几百字客户描述，才能判断要不要接。
- **现在做什么**：把 ②③④ 的结果喂回去（含 RAG 检索片段），生成一段不超过 60 字的工单摘要。
- **业务意义**：负责人在飞书通知列表里**扫一眼卡片就知道要不要立刻处理**，不用每条都点进去读长文。这是"通知有没有人看"的关键。
- **调优点**：摘要节点用 **temperature=0.4** 的独立模型节点（"OpenAI Chat Model（摘要）"），比分类更自然、更像人写的总结。

### ⑥ 生成结构化工单记录（Set）

- **替代的人工动作**：把客户名、联系方式、问题描述手动敲进 Excel / 工单系统，字段格式还五花八门。
- **现在做什么**：把前面所有节点的结果打包成一条标准工单：工单号（`TK-日期-流水`）、客户、联系方式、来源、分类、情绪、紧急度、摘要、原文、状态、创建时间。
- **业务意义**：从此每一条客户进线都是**同构、可查询、可统计**的记录，为后续报表、SLA 考核、AI 复盘打地基。

### ⑦ SLA 矩阵（28 组合 · Code 节点）

- **替代的人工动作**：班长凭经验决定"这单多急、该找谁"——标准不统一，同样的事故昨天 2 小时、今天拖半天。
- **现在做什么**：用一张 **7 分类 × 4 紧急度 = 28 组合**的查表矩阵，直接算出：
  - `level`：P1（30min）/ P2（1~2h）/ P3（4~8h）/ P4（24h）
  - `team`：责任团队（如 `技术支持+主管`、`客户成功+主管`）
  - 特殊规则：投诉+高/紧急 → P1、技术支持+critical → P1。
- **业务意义**：
  - **响应时限不再是"拍脑袋"**，而是全员同一套标准；
  - 通知卡片直接带 `[P1]` 徽章，谁该动、多快动，一眼清楚；
  - 为后续 SLA 考核报表打基础（超时率、达标率都能统计）。

### ⑧ 同步飞书 / 数据库（HTTP Request → 飞书多维表格 · 带重试）

- **替代的人工动作**：客服把刚录好的 Excel，再复制粘贴到公司内部系统；或者下班前统一"补录"。
- **现在做什么**：工单一生成，立刻调用飞书多维表格 OpenAPI 写入一行（含 SLA 字段 `level/team`）；如有需要，同一个分支可以并行写业务数据库 / CRM。节点带 `retryOnFail`，瞬时失败自动重试。
- **业务意义**：
  - 数据实时落地，不再有"昨晚的工单今早才录"的时间差；
  - 飞书表格就是一张共享看板，全员看到同一份数据，不用来回发截图。

### ⑨ 自动通知负责人（HTTP Request → 飞书消息卡片 · 带重试）

- **替代的人工动作**：班长看到单子后，微信/电话挨个找对应同事；紧急的事常常因为人在开会而被耽误。
- **现在做什么**：按 SLA 结果发一张飞书交互卡片，**标题直接带 `[SLA等级]`**：
  - 红色 = critical（投诉、舆情级）
  - 橙色 = high
  - 蓝色 = 普通
  - 卡片正文带：分类、紧急度、SLA 时限与责任团队、客户联系方式、AI 摘要、原文链接。节点带 `retryOnFail`。
- **业务意义**：**高危工单从"被发现"到"触达负责人"是秒级**，而不是等上班、等开会结束。客户投诉不再过夜。

## 配套：错误处理工作流（error-handler.json）

- **触发**：n8n `Error Trigger`——任何工作流执行出错都会进入。
- **做什么**：自动把错误信息（工作流名、节点、错误消息、时间）发成一条飞书告警卡片给管理员。
- **业务意义**：以前"某个流程昨晚挂了，今早才发现"；现在**出错即告警**，管理员第一时间介入，而不是等客户来问"怎么没人理我"。

---

## 为什么要这样拆节点，而不是一个大 Prompt 全包

很多团队第一版会写一个超长 Prompt 让模型一次性输出所有字段。本工作流刻意拆成 **分析 → 分类 → 摘要** 三段，原因是：

| 做法 | 优点 | 缺点 |
|---|---|---|
| 一个大 Prompt 全搞定 | 省一次模型调用 | 改分类规则要重跑全部；出错时不知道哪段错 |
| **三段式（本方案）** | 每段职责单一、可独立调 Prompt、可单独替换模型、可单独监控准确率 | 多两次调用，成本可忽略 |

对企业来说，**可维护性 > 省几次 token**。分类规则下个月要加新类目，只动 ③；想换国产模型，只动上面两个 Chat Model 节点；想改 SLA 口径，只动 ⑦。

## 分温度模型策略

| 节点 | 温度 | 为什么 |
|---|---|---|
| ② 分析 / ③ 分类 | 0.1 | 分类要**稳定一致**，同一句话不能一会归销售一会归技术 |
| ⑤ 摘要 | 0.4 | 摘要是给人看的，稍微放开一点**更自然** |

两个模型节点共用同一套凭据与环境变量，切国产模型只需改 `.env` 三行（`LLM_MODEL` / `OPENAI_BASE_URL` / `OPENAI_API_KEY`）。

## 所需外部配置

在 n8n 中导入工作流后，需在 **Credentials / 环境变量** 里配好：

| 变量名 | 用途 |
|---|---|
| `OPENAI_API_KEY`（在 OpenAI 凭据里配，可填 `{{ $env.OPENAI_API_KEY }}`） | ②③⑤ 三个 LLM 节点共用 |
| `OPENAI_BASE_URL`（凭据 Base URL，可填 `{{ $env.OPENAI_BASE_URL }}`） | 国产模型地址（DeepSeek/通义/智谱/Kimi） |
| `LLM_MODEL` | 模型名（默认 `deepseek-chat`） |
| `KB_SEARCH_URL` | ④ RAG 检索接口（可留空，自动跳过增强） |
| `KB_TOP_K` | ④ 取回片段数（默认 3） |
| `FEISHU_BITABLE_APP_TOKEN` | ⑧ 写多维表格 |
| `FEISHU_BITABLE_TABLE_ID` | ⑧ 写多维表格 |
| `FEISHU_OWNER_USER_ID` | ⑨ 通知的默认负责人 |
| 飞书 `tenant_access_token` 获取方式 | 建议加一个前置 HTTP 节点自动刷新，避免手动维护 |

> 飞书应用需要开通权限：`bitable:app`（多维表格读写）、`im:message`（发消息）。
